# What StorageHub still needs: proposal (needs-review section F)

Section F of StorageHub's review lists guarantees StorageHub makes today that CL.Storage does not offer
yet. None of them is built. For each: what is already there after the review fixes, the API I would add,
and a rough cost (S ≤ 1 day, M 2–4 days, L a week or more, each including tests). The order is the
review's order of importance.

| # | Need | Already there | Proposed API | Cost |
|---|---|---|---|---|
| 1 | Caller commits the sync baseline | Baseline saved by the library after apply; `report.BaselineError` | `StorageSyncOptions.BaselineCommit = Automatic \| Manual`. With `Manual`, nothing is saved and `report.ProposedBaseline` (`StorageSyncBaseline`) carries what would have been. `StorageSync.ComputeBaseline(plan, report, previous)` is public. The store gets `SaveAsync(StorageSyncCommit commit, ct)`, where the commit is run id, plan digest, expected baseline revision, entries, and a caller context object. No automatic save after a failed or cancelled run unless asked (`SaveAfterFailedRun`). | M |
| 2 | Server-enforced conditional replace | `DestinationCondition` is handed to the provider's move and reported in `ConditionEnforcement`; S3 per-server probe (`ConditionalRequests`) | `StorageTransferOptions.RequireAtomicCondition`: fail with `storage.unsupported` before any byte moves when the destination cannot enforce the condition in the committing request. `Capabilities.CanEnforceAtomically(StorageConditionKind)` (async on S3 because of the probe). S3 complete-multipart with `If-Match`, and a direct verified single-PUT path for object stores (hash while uploading, `x-amz-checksum-sha256`) so no staging copy is needed. | M |
| 3 | Conditions without ETags | — | `ExpectedLength`, `ExpectedLastModified`, `ExpectedSha256` on `StorageMutationCondition`; `IsEmpty` and matching cover them, so FTP and SFTP can say "replace only what the user saw" (checked before commit; reported `CheckedBeforeCommit`). | S |
| 4 | Machine-readable failure reasons | Details strings (`sourceChanged=N`, `expectedLength=…`) | `StorageTransferReport.FailureReason` enum (`SourceChanged`, `SourceTruncated`, `SourceGrew`, `DigestMismatch`, `DestinationChanged`, `DestinationUnconfirmed`, `Other`) and `IsTransient`. Set at the few places that create those conflicts today. | S |
| 5 | Verification policy | A length mismatch after commit already fails without `Verify` (A5); `ExpectedSha256` implies `Verify` | `StorageVerification { None, Size, StrongHashWhenAvailable, StrongHashRequired }` replacing the `Verify` bool (kept as an obsolete alias). `StrongHashRequired` fails where the destination has no server SHA-256 and cannot be read back. | S |
| 6 | Queue reconcile commands and expected revisions | `RetryAsync` on NeedsReconciliation/Interrupted; revisioned store | `MarkCompletedAsync(id, expectedRevision)`, `MarkFailedAsync(id, reason, expectedRevision)`, `RestartAsync(id)` (discards the token and deletes the staging object), `ReviewAsync(id)` (the report and what is left on both sides). `long? expectedRevision` on every control call, answered `storage.conflict` on mismatch. | M |
| 7 | Classification hook and connection resolver | Fixed rules: transient → retry, trust/credential → Blocked, partial failure → NeedsReconciliation | `StorageTransferQueueOptions.Classify: Func<Error, StorageTransferReport?, StorageTransferDecision>` (Retry, Fail, Block(reason), NeedsReconciliation), with the current rules as the default. `EnsureConnectionAsync: Func<string, CancellationToken, ValueTask<Result>>` called before each attempt; a failure blocks the job (`BlockReason.Connection`, a new member at the end). | S |
| 8 | Approval binding for sync plans | `SchemaVersion`, connection ids, `CaseInsensitive`, `OptionsDigest` in the plan digest; apply refuses a mismatch | `StorageSyncPlan.Binding`: a digest over an options fingerprint, each connection's provider, root and capabilities, and a caller `ExternalBinding` string; recomputed at apply against the live connections and compared with `CryptographicOperations.FixedTimeEquals`. The binding covers only named fields, so a new property in a later version does not invalidate stored approvals. | M |
| 9 | Strict identity and proven baselines | `StorageSyncIdentity.Sha256` filled by `Verify`; weak local ETags marked `W/` | `StorageCompareOptions.RequireStrongIdentity` (a pair known only by size and time becomes `Indeterminate`, a conflict); `StorageItem.ETagIsSynthetic`; `Sha256` from server digests where known; `StorageSyncOptions.RequireProvenBaseline` leaves unproven entries out with reason `content_unproven`. | M |
| 10 | Per-kind conflict policy | One `ConflictPolicy` for every kind | `StorageSyncOptions.ConflictPolicies: IReadOnlyDictionary<StorageSyncConflictKind, StorageSyncConflictPolicy>`; with `PropagateDeletes = false` a deletion becomes a `DeleteVersusModify`-style conflict (`DeletedOnOneSide`) instead of a copy-back. | S |
| 11 | Deletion safety parity | `MaxDeletes`, `MaxDeletePercent` (counted on files, in the options digest, so re-checked at apply), empty-side refusal | `DeletionSafety { Denominator = Baseline \| Listing, OnExceeded = Withhold \| RefusePlan, RequireBaselineForMirrorDeletes, RootIdentity }`; the root identity (for example a volume serial, or a marker file) is recorded in the baseline and checked before any delete. | M |
| 12 | Step journal and fence | — | `StorageSyncOptions.OnStepStarting` / `OnStepCompleted` (async; `OnStepStarting` can veto a step, which then is `NotRun`), and `IStorageSyncStateStore.TryAcquireAsync(syncId, runId, lease)` called before the first mutation and renewed during the run. | M |
| 13 | Queue durability details | Checkpoints with phase and token; `ToJson`/`FromJson`; schema check | Persist the staging path and token when an attempt enters Transferring and every N MiB; `CleanupPending` outcome; `ErrorSanitizer: Func<Error, Error>` applied before anything is stored; caller `Tags` on the spec (in idempotency); `PriorityInIdempotency`; `PruneStates`; paged `QueryAsync(filter, page)` and `CountByStateAsync` on the store, with `LoadAsync` limited to live jobs. | L |
| 14 | Write stream outcome | `CommitAsync` returns the committed item with `Sha256`; failures carry the storage error | `CommitAsync` returns `Result<StorageWriteReport>` (committed item, staging left behind, `ConditionEnforcement`, digest); `AbortAsync` returns `Result`. Breaking for callers of `CommitAsync`; alternatively a new `CommitWithReportAsync`. | S |
| 15 | Resumable conditional overwrite, staging hygiene, move report | Resume and `DestinationCondition` are exclusive today | Allow `ConflictPolicy.Resume` with `DestinationCondition` (the condition applies at promote). `CleanupInternalAsync(path, olderThan, keepTokens)` that never deletes a part file named by a kept token. `StorageTransferReport.SourceDeleteEnforcement`. | M |
| 16 | Scale caps and pluggable concurrency | `MaxItems`, hashing budget | Caps on directories, pages, per-file hash size and pattern count; `StorageCompareOptions.FilterCaseSensitive`; `IConcurrencyController` (the adaptive controller becomes the default implementation) fed with throughput as well as failures. | M |

Roughly five to six weeks for all of it. Items 3, 4, 5, 7, 10, and 14 are small and independent, and
together remove most of what keeps StorageHub's `TransferExecutor` alive; 1, 2, 8, and 12 are what the
sync engine is waiting for. Suggested order: 4, 5, 3, 2, 14 (transfers), then 7, 6 (queue), then 1, 12,
8, 9, 10, 11 (sync), then 13, 15, 16.
